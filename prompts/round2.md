# 第二轮：打分与改造建议

## 输入

1. **规则卡**（上一轮产物）：

```
{{在此粘贴第一轮的 A 表 + B JSON}}
```

2. **仓库证据包**：

```
{{在此粘贴 evidence.md 全文}}
```

3. **评分表**：见下文。

## 背景（必须遵守）

我们现有框架：pytest + Playwright（Python），已运行多年，有 POM 和大量脚本。
但 POM 覆盖不全、缺少 code review。
**禁止建议重写现有测试。**

## 评分表

每项按 0–3 打分：

- `0` 缺失
- `1` 有雏形但不可依赖
- `2` 可用但有明显缺口
- `3` 成熟且有自动化保障

| # | 检查项 |
|---|---|
| 1 | 生成物是否可评审、可回滚、可 diff |
| 2 | 是否有确定性闸门（schema / lint / check），而不是靠人自觉 |
| 3 | 是否零侵入既有 POM（只新增、不修改） |
| 4 | 断言是否有来源（sources），能防"编造期望" |
| 5 | 失败是否可归因（真缺陷 / 用例错 / 环境 / 不稳定） |
| 6 | LLM 是否不在 CI 里，运行时可复现 |
| 7 | 单页 / 单用例的上下文成本 |
| 8 | 风格收敛靠什么（prompt 还是模板 + lint） |
| 9 | 技术债是否可见（raw 占比、POM 缺口） |
| 10 | 生成过程能否断点续跑 |

## 硬约束

1. 只能引用证据包里出现过的文件。找不到就写 `no-evidence`，**禁止编造路径或行号**。
2. "对方"的分数只能来自规则卡，并标注证据等级：
   - 文档自称实测的 → `[文档实测]`
   - 其余 → `[未验证]`
3. **允许结论是"无需改造"。** 如果某项我们不比对方差，明确指出，不要凑建议。
4. 任何"重写现有测试"的建议视为不合格。
5. 特别注意：我们的框架已有 POM。生成器应该生成**对已有 POM 的调用**，
   而不是另起一套定位体系。若你的建议与此相反，请重读文档 §9.2。

## 输出

**A. 对比表**

| # | 检查项 | 我方 | 对方 | 我方证据（文件:行号 或 no-evidence） | 对方证据等级 |
|---|---|---|---|---|---|

**B. JSON**

```json
{"items":[{"id":1,"ours":0,"theirs":2,"evidence_ours":"...","evidence_theirs":"[未验证]"}]}
```

**C. 改造建议**（只针对「我方 ≤1 且对方 ≥2」的项，最多 5 条）

每条必须包含五项，缺一不可：

| 字段 | 要求 |
|---|---|
| 改哪里 | 具体文件 / 模块 |
| 改动范围 | 新增还是修改，预估行数 |
| 回滚方式 | 怎么撤回 |
| 如何验证 | 可执行的命令或断言 |
| 风险 | 代价是什么 |

**D. 如果只能做一件事，做哪件？**（30 字以内）
