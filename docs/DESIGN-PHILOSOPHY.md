## 0. 如何使用本文档

本文档不是产品说明书，是一次完整探索的**思想记录**。如果被用于与另一套框架对比，请遵守三条：

1. **区分证据等级**。文中标注 `[实测]` 的是真跑过的数据，`[推断]` 是设计推理，`[未验证]` 是明确没做的。不要把推断当结论。
2. **先看约束，再看方案**。本文所有结论都绑定在"内网 / 纯文本模型 / 已有成熟 pytest 框架"这三个前提下。换前提，结论可能反转。
3. **看代价，不只看收益**。每个设计决策（§10 ADR）都写了代价和"何时不该用"。

## 1. 问题定义与约束

### 1.1 要解决的问题

让 AI 参与 UI 自动化测试，产出**可评审、可回归、可进 CI 的测试资产**，而不是一次性的演示脚本。

### 1.2 约束条件

| 约束 | 影响 |
|---|---|
| 只能用纯文本模型，无法使用多模态 | 不能走"截图 → 视觉模型 → 坐标"的路线 |
| 内网环境，插件/依赖安装受限 | 方案不能依赖特定 agent 或云端服务 |
| 已有多年运行的 pytest + Playwright 框架与大量脚本 | 新方案必须零侵入、风格统一 |
| 测试人员水平参差、缺乏 code review | 规范必须由机器兜底，不能依赖人的自觉 |
| 被测系统为 EMS 电站管理系统，历史文档多 | 需要业务知识沉淀，且要防止版本漂移 |

## 2. 核心命题：替换感知层，而不是替换整个方法

### 2.1 视觉接地 vs 结构接地

主流多模态方案（如 MidScene.js）的范式是：

```
截图 → 多模态模型 → 输出坐标或自然语言断言 → 直接执行
```

本方案替换为：

```
可访问性树 / DOM 语义快照 → 纯文本模型 → 输出语义引用（role+name / testid）→ 框架解析执行
```

四件事——**感知 / 决策 / 执行 / 判定**——多模态只影响第一件。

### 2.2 为什么测试场景更适合结构接地 `[推断 + 实测支持]`

1. 测试目标的 UI 是**有语义的**：表单有 label、按钮有 role、列表有文本。开放世界 GUI 才需要视觉。
2. a11y 树包含截图看不到的信息：`required`、`disabled`、`aria-live`、`data-testid`。
3. 文本快照可 diff、可缓存、可审计；截图不行。
4. 文本 token 成本显著低于图片。
5. **最关键**：语义定位能固化成代码资产，视觉坐标不能。测试要的是资产，不是每次现场表演。

### 2.3 三条不变量

1. **模型不写选择器**，只写语义目标。
2. **模型不碰生成物**（`tests/`），只写结构化用例。
3. **LLM 不进 CI**：生成期用模型，执行期只跑固化代码。

理由分别是：选择器是幻觉重灾区且失败模式隐蔽；生成物必须可回滚、可 diff、可评审；运行时调模型无法复现"当时模型看到了什么"。

## 3. 框架形态

### 3.1 数据流

```
需求 / 接口文档 / 页面快照
        ↓
  spec/cases/*.json          模型唯一被允许写的地方（意图级，无选择器）
        ↓  render
  tests/test_*.py            生成物，禁止手改
        ↓  pytest
  report + trace             失败证据
        ↓  triage
  四分类：真缺陷 / 用例错 / 环境 / 不稳定
```

### 3.2 为什么用 JSON 中间层，而不是直接生成代码

| 维度 | 直接生成代码 | JSON 中间层 |
|---|---|---|
| 可评审 | 需要读懂代码 | 看意图即可，速度差 5–10 倍 |
| 可去重 | 难 | 按 target 语义去重 |
| 换模型 | 代码风格漂移 | 风格由模板决定，稳定 |
| 校验 | 只能靠运行 | schema + lint 静态拦截 |
| 增量 | 难 | 按需求/变更选靶 |

**代价**：每增加一种能力，就要在 schema 加字段 + renderer 加分支。字段超过约 15 个后，JSON 会逐渐变成一门 DSL。这是这类框架的宿命（§7）。

### 3.3 生成物边界

`tests/**` 只允许由 renderer 产出。`render --check` 重新渲染到内存、与磁盘比对，不一致即失败。这是"生成物不可手改"的唯一可靠执行方式。

## 4. 确定性工具链

### 4.1 为什么核心工具必须确定性

`[实测]` 本次验证中，4 个问题里 3 个是"跑一下就知道"的，1 个是"照 schema 看一眼就知道"的，**没有一个是靠再找一个模型看一遍能解决的**。

因此原则是：**能确定性验证的，永远不要交给 agent。**

| 工具 | 职责 | 是否用模型 |
|---|---|---|
| `snapshot.py` | 页面 → 稳定 key 的语义快照 + diff | 否 |
| `render.py` | 用例 JSON → pytest 函数 | 否 |
| `preflight.py` | 环境自检，退出码即结论 | 否 |
| `index_pom.py` | AST 扫描既有仓库，产出 POM/manifest | 否 |
| `gap_report.py` | 覆盖率、缺口、技术债 | 否 |
| `lint.py`（规划） | 边界、风格、sources、raw 预算 | 否 |

### 4.2 snapshot 的关键设计：稳定 key

key 优先级：`tid:<data-testid>` > `<role>:<name>`，重复追加 `#2`。

**绝不用 DOM 序号做 key。** 序号每次快照都会变，模型上一轮记的引用下一轮就错位；这种错误极其隐蔽——点了"看起来对"的另一个元素，测试却过了。

`[实测]` TesterHome 首页 194 个节点中有 18 个重名 key。这些就是 18 个潜在歧义点。

### 4.3 render 的定位优先级

`get_by_test_id` > `get_by_role(name, exact)` > `get_by_label(exact)` > `get_by_text`；链接可用 `href` 消歧。

`[实测]` 两个必须的补充：
- `exact=True`：否则 `社区` 会命中 `社区学堂`
- `label` 也要 `exact`：否则 `get_by_label("手机号")` 会同时命中被 `aria-labelledby` 标记的表单

## 5. 实测：TesterHome 验证

### 5.1 结果

| 阶段 | 数据 |
|---|---|
| 首次执行（Node 版） | 5 条用例，**4 通过 1 失败**，15.4s |
| 修正后 | **5 通过**，28.7s |
| 迁移 Python 后 | **5 通过**，26.0s |
| 本地演示用例 | 2 通过 |
| 快照 | 194 节点，26.6KB（紧凑）/ 37KB（缩进） |
| 增量 diff | 两次抓取 `+0 -0 ~0` |

### 5.2 四个问题及其分类

| # | 问题 | 分类 | 发现方式 |
|---|---|---|---|
| 1 | `toHaveURL(//topics/)` 生成非法正则 | **框架 bug** | 运行 |
| 2 | `get_by_role("link", name="问答")` 命中 2 个元素 | **框架能力缺口** | 运行（strict mode） |
| 3 | `get_by_label("手机号")` 命中表单与输入框 | **框架 bug** | 运行 |
| 4 | 对 `<ul>` 断言 count=2 | **用例错误** | 运行 |

**结论：0 个问题由"探索"或"代码评审"发现，全部由执行发现。** 这不否定探索的价值（它能减少返工），但说明执行不可替代。

### 5.3 数据画像

`[实测]` 首页快照构成：194 节点中 **192 个是 link**，1 个 textbox，1 个 heading；174 个唯一 name；18 个重名。

这说明三件事：

1. 所谓"页面地图"其实是"一袋链接"，**没有页面结构概念**。
2. 重名是常态而非意外，歧义是结构性问题。
3. 我们采集了 `path`（DOM 路径）——唯一的结构信号——却明令禁止用它定位。**采集了结构，又把它废掉了。**

### 5.4 证明了什么 / 没证明什么

**证明：**
- 零 `data-testid` 的站点能跑通（5/5）
- 管线闭环成立：JSON → 渲染 → pytest → 结果
- 失败是响亮的（strict mode 拒绝），不是静默点错
- 快照稳定、可 diff
- Python 化与 pytest 生态兼容良好

**没证明：**
- 没有一条用例涉及写操作（表单提交、状态变更、数据清理）
- 没有登录态
- 没有动态数据断言（网络响应、DB 状态）
- 没有失败归因能力

**一句话：验证了"页面能打开"，没有验证"业务能跑通"。**

## 6. 框架剖析：五个结构性缺陷 `[实测支撑]`

### 6.1 没有区域（region）概念——最致命

快照是平的。模型看到 192 个 link，不知道哪个在导航、哪个在正文、哪个在页脚。重名只能靠 `exact`/`href` 打补丁，而补丁追不上页面。

**根治**：`within` / `region` 作用域，而不是继续发明消歧字段。

### 6.2 没有状态

节点只有 `name/value/disabled/checked`。缺：

- 当前页面/active tab
- 弹窗遮罩（modal 打开时背后元素不可点）
- 分页位置

多步骤流程（弹窗确认、翻页、tab 切换）写不了，或必然 flaky。

### 6.3 断言词汇太窄

只有 `visible / text / value / count`。真实业务需要：

- 表格型：第 3 行第 2 列等于 X
- 网络型：请求体带 orderId、响应 200
- 关系型：A 变化后 B 跟着变

词汇不足会诱导用户写弱断言。

### 6.4 用例是线性的，没有 fixture

`setup(登录→建数据) → 测试 → teardown(清理)` 表达不了，只能把所有步骤塞进一条用例，直接违反"一条用例一个意图"。

### 6.5 工具链自身零测试

`render.py` 是单点故障，却没有任何测试。两个 bug 全靠人工跑出来。**一个宣称"生成物必须可验证"的框架，自己的生成器不可验证**——这是自我矛盾。

## 7. 与 pytest 生态的接缝，以及 DSL 宿命

生成物是普通 pytest 函数，这是最大优势：markers、xdist、junitxml、allure、CI 缓存全部可用。

但存在根本张力：**生成物不能手改 ⇒ 所有能力必须能从 JSON 表达。**

想要"跑 3 次查 flaky" → 加 `marks`；想要"CI 跳过" → 加 `skip`；想要"依赖登录 fixture" → 加 `fixtures`；想要表格断言 → 加 `table_cell`。

**每加一个能力 = schema 一个字段 + renderer 一个分支。约 15 个字段后，你就是在一门残缺的 DSL 上维护。**

建议：**能力长在"步骤组合"和"fixture"上，而不是无限长字段。** 否则三年后你会有一门语法残缺、文档缺失、只有原作者会写的测试语言。

## 8. Agent 拓扑

### 8.1 角色应由产物边界决定，不由职能决定

判据：**每个 agent 必须有一个独有、可验证的产物文件，且该产物不能被另一个 agent 直接改写。**

### 8.2 不需要"代码实现"角色

在本框架中代码由 renderer 生成。若设一个"代码实现子 agent"去写 Python 测试，会直接绕开 renderer，失去：生成物闸门、可评审性、换模型不换代码风格的能力。

正确角色是 `case-author`：写 JSON，禁止碰 `tests/`。

### 8.3 "总控 agent"通常是多余的

主会话天然就是调度者。再套一层 dispatcher，唯一确定的效果是信息损耗。只有当需要**跨会话、长时间运行的调度状态**（任务队列、重试计数、断点恢复）时才值得单独抽出。

### 8.4 评审者不能与被评审者共享上下文

同一模型、相近上下文，评审者会倾向于认可已写出的内容（sycophancy）。物理隔离上下文，比 prompt 里写"请严格评审"有效一百倍。

### 8.5 能确定性验证的，不要交给 agent

"符不符合规范"（schema、是否用选择器、断言是否过弱）全是可判定问题。用 LLM 做会慢、贵、不稳定且不可复现。用 `lint` + 退出码。

### 8.6 三种死法

| 死法 | 表现 | 对策 |
|---|---|---|
| 死锁 | A 等 B 产物，B 等 A 确认 | 产物 DAG 单向，禁止跨层请求 |
| 甩锅 | 各自认为对方错，来回三次 | 四分类由 verifier 单方定，争议升级给人 |
| 盖章 | 互相认可，谁都没真检查 | 评审者只读产物 + 跑命令，不读对方推理过程 |

### 8.7 建议拓扑

| 角色 | 产物 | 权限 | 停止条件 |
|---|---|---|---|
| `analyst` | `pages/*.json` 契约、`assertions.json` | 只读页面/文档 | 要登录 / 重名 >3 无法消歧 / 主内容是 canvas |
| `author` | `spec/cases/*.json` | 只读契约 | 找不到期望值来源 → 停 |
| `verifier` | `triage.json` | 只读产物 + 执行 | 同一用例失败 3 次 → 停 |

**起步只需 2 个：author + verifier。** 它们天然对立，收益最直接。

## 9. 面向成熟框架（EMS 场景）的改造

### 9.1 前提变了，结论也要变

已有 POM、已有大量脚本、零侵入要求、风格统一要求。**这推翻了"生成自包含测试"的整个前提。**

### 9.2 从"生成测试"改为"生成对既有框架的调用"

```json
// 不要：DOM 操作
{"action": "click", "target": {"role": "button", "name": "查询"}}

// 要：业务动作
{"action": "call", "page": "AlarmCenterPage", "method": "filter_by_level", "args": {"level": "严重"}}
```

```python
@pytest.mark.ems_alarm
@pytest.mark.p1
def test_ems_alarm_003(logged_in_as, alarm_center: AlarmCenterPage):
    """EMS-ALARM-003 按告警等级筛选

    sources: REQ-EMS-112, TC-EMS-0871
    """
    alarm_center.filter_by_level("严重")
    assert alarm_center.row_count() > 0
```

**零侵入 + 风格统一的物理基础：只 import，不复制；只调用，不重写。**

### 9.3 三级降级：缺口不绕过，缺口用 POM 补

POM 覆盖不全是常态，不是例外。

| 级别 | 条件 | 生成什么 | 侵入性 |
|---|---|---|---|
| L1 | manifest 有该方法 | 直接调用 | 零 |
| L2 | 类存在、方法缺失 | POM 扩展（新文件，子类/组合） | 新增文件 |
| L3 | 页面无 POM | 新 POM 类 + 测试 | 新增文件 |
| 逃生舱 | 一次性动作 | 内联定位 + `# TODO(pom-gap)` | 测试文件内 |

**判定规则（写死，不靠感觉）**：同一动作在 ≥3 条用例出现 → 必须走 L2/L3；否则允许 raw。

L2 示例（不修改既有文件）：

```python
# pages/_ai/alarm_center_page_ai.py
class AlarmCenterPageAI(AlarmCenterPage):
    def filter_by_level(self, level: str) -> None:
        self.page.get_by_role("combobox", name="告警等级").select_option(level)
        self.page.get_by_role("button", name="查询").click()
```

评审通过后把方法搬进原类、删除子类、更新 manifest，重新生成。

### 9.4 零侵入边界合同

| 允许 | 禁止 |
|---|---|
| 新增 `tests/ai_generated/` | 修改既有 `tests/` |
| import 既有 POM / fixtures / helpers | 修改 `pages/`、`conftest.py`、`utils/` |
| 在 pytest.ini 注册新 marker | 改既有 marker 语义 |
| 新增 `ai/` 目录 | 动 CI 主流程 |

可校验：`git diff --name-only` 白名单，CI 一道 lint 即可守住。

### 9.5 知识库：不是"一个 RAG"，是四个索引

| 索引 | 内容 | 服务目标 | 构建方式 |
|---|---|---|---|
| 业务知识 | 需求、术语、规则 | 期望值来源 | 结构化 + 增量 |
| 历史用例 | 手工用例、禅道导出 | 测什么、步骤 | 保留用例 ID |
| **框架 API** | POM 方法、fixture、marker | **零侵入 + 风格** | **AST 扫描，CI 自动重建** |
| 风格样板 | 20–30 个现有脚本 | 长得像不像 | 人工挑 + 聚类 |

**第三个最容易被忽略，却决定生成物融不融得进去。** 它不需要 AI——`ast` 扫一遍即可，而且永远与代码同步；RAG 会检索到过时的写法，AST 不会。

### 9.6 强制引用来源

每条断言必须带 `sources: [...]`；`lint` 检查"没有 sources 的 expect 直接 fail"。

这把"禁止发明期望值"从 prompt 变成了机器规则。

### 9.7 EMS 特有的三个风险

1. **版本漂移**：老文档可能对应旧版本 → 每个 chunk 带 `version` / `effective_date`，检索时过滤。
2. **术语密集**（有功功率、无功、越限、AGC、AVC）：纯向量检索会漏，需术语表 + 同义词 + 混合检索。
3. **数据确定性**：电站在跑，遥测一直在变 → 优先 fixture 造数 + 接口 mock，不要对实时数值断言。

### 9.8 分阶段落地

| 阶段 | 内容 | 验收 | 是否用 AI |
|---|---|---|---|
| P0 | `index_pom` + `gap_report` | 列出所有 Page/fixture；给出缺口 | 否 |
| P0.5 | `lint` | 拦住改既有文件、无 sources、raw 超预算 | 否 |
| P1 | 抽 3–5 个标准样板，定死模板 | 生成空壳与样板 diff 只差业务内容 | 否 |
| P2 | 历史用例结构化 | 100 条可检索可追溯 | 半自动 |
| P3 | 生成骨架（POM 调用 + 断言占位 + TODO） | 人补断言 | 是 |
| P4 | 断言自动生成 + 执行 + 四分类 | 首过率、返修率 | 是 |

**P0/P1 完全不需要 AI，但决定后面能不能"零侵入"。** 跳过这两步直接上生成，通常得到一堆融不进框架的孤儿脚本。

## 10. 设计决策记录（ADR）

### ADR-1 模型不写选择器
**理由**：选择器生成是幻觉重灾区，失败模式隐蔽（能匹配到错元素）。
**代价**：需要前端/框架提供语义（label/role/testid）。
**何时不该用**：被测系统 a11y 极差且无法改善时，需要退回 DOM 文本层。

### ADR-2 模型不碰测试代码
**理由**：生成物必须可回滚、可 diff、可评审。
**代价**：所有能力必须能从 JSON 表达（§7）。
**何时不该用**：一次性探索脚本，不需要沉淀时。

### ADR-3 LLM 不进 CI
**理由**：成本、延迟、可复现性三项不可接受。
**代价**：生成与执行分离，需要额外一步"固化"。

### ADR-4 自愈只修定位器，不改断言
**理由**：改断言让测试变绿，等于把 bug 写成预期——最恶性的失败模式。
**执行方式**：断言变更必须人工确认。

### ADR-5 快照优先于截图
**理由**：见 §2.2。
**何时不该用**：像素级视觉回归（用 `to_have_screenshot`，纯算法，不需要模型）。

### ADR-6 接口 mock 优先于真实数据
**理由**：纯文本 agent 对时序敏感，数据一变全局飘。
**代价**：要维护 mock，覆盖率下降。
**结论**：探索期必须 mock；固化后可切真实数据跑一轮。

### ADR-7 缺口用 POM 补丁填，不绕过
**理由**：绕过会产生平行实现，半年后风格分裂。
**代价**：需要人工评审 POM 补丁。

## 11. 反模式清单

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| 让模型直接产出测试代码文件 | 风格漂移、无法评审 | 产出 JSON，渲染成代码 |
| 用 `.first()` / `.nth()` 消除歧义 | 静默点错元素 | `exact` / `href` / `testid` / `within` |
| 自愈时改断言 | 把 bug 写成预期 | 只修定位器，断言变更需人审 |
| 只写 `visible` 断言 | 用例全绿但抓不到 bug | 至少补 text/value/count |
| 用 LLM 做规范检查 | 慢、贵、不可复现 | lint + 退出码 |
| 全量预探索所有页面 | 地图过期、无人阅读、上下文爆炸 | 按需探索 + 契约沉淀 |
| 把总控做成 subagent | 多一跳信息损耗 | 主会话即总控 |
| 让评审者读被评审者的推理 | 互相盖章 | 只读产物 + 跑命令 |
| 无预算的 raw 降级 | 技术债失控 | raw 占比 >20% 即 fail |
| 承诺"全自动无人值守" | 三个月后无人维护 | human-in-the-loop |

## 12. 度量体系

### 12.1 该看的

| 指标 | 含义 | 方向 |
|---|---|---|
| 缺陷发现率 | 每 100 条用例抓到多少真 bug | 升 |
| 变异杀伤率 | 注入缺陷被捕获比例 | >60% |
| Flaky 率 | 非确定性失败占比 | <5% |
| POM 覆盖率 | 有 POM 的页面/动作占比 | 升 |
| raw 步骤占比 | 技术债 | 降，设预算 |
| 生成物首过率 | 不改就能跑通 | 升 |
| POM 补丁合入率 | L2 补丁最终被合并比例 | >70% |
| 人工返工次数 | 每条用例平均改几次 | 降 |

### 12.2 不该看的

- **用例数量**：诱导大量重复、低价值用例。
- **代码覆盖率**：证明"被执行过"，不证明"能抓 bug"。用变异测试补位。

## 14. 给对比 AI 的指引

### 14.1 对比时请逐项回答

对两套框架各打一次分（0–3：缺失/有雏形/可用/成熟），并给出证据：

1. 生成物是否可评审、可回滚、可 diff？
2. 是否有确定性闸门（schema/lint/check）而不是靠人自觉？
3. 生成物是否绕过既有 POM / 是否零侵入？
4. 断言是否有来源（sources），能否防"编造期望"？
5. 失败是否可归因（四分类）？
6. LLM 是否在 CI 里？运行时是否可复现？
7. 单页/单用例的上下文成本是多少 token？
8. 风格如何收敛？靠 prompt 还是靠模板 + lint？
9. 技术债是否可见（raw 占比、POM 缺口）？
10. 对话/生成过程能否断点续跑？

### 14.2 建议吸收的部分

- 三条不变量（§2.3）
- JSON 中间层 + 确定性渲染（§3.2）
- 稳定 key 与 `exact` / `href` 的消歧顺序（§4.2、§4.3，有实测支撑）
- 能确定性验证的绝不交给 agent（§4.1）
- 三级降级 + 缺口用 POM 补（§9.3）
- 零侵入边界合同（§9.4）
- 四索引知识库，尤其是 AST 生成的框架 API 索引（§9.5）
- 强制 sources（§9.6）
- raw 债务预算（§11）

### 14.3 建议存疑的部分

- **`within`/`region` 的具体形态**：方向确定，设计未验证。
- **多 agent 拓扑**：纯设计，未实跑；在小规模任务上可能不如单 agent 划算。
- **"生成骨架 + 人补断言"的分工比例**：取决于团队水平，需实测返修率。
- **知识库的检索策略**：术语密集场景下的混合检索效果未验证。

### 14.4 不要照搬的部分

- **TesterHome 用例本身**：那是验证管线用的玩具用例，无业务价值。
- **快照的字段设计**：为论坛类页面设计，后台系统（表格、弹窗、分页）需要扩展。
- **"零 testid 也能跑"的乐观假设**：业务系统长期维护，必须推动 testid 契约。
- **文档里的时间/成本估算**：都是基于单机单次的粗糙观测。

### 14.5 如果只能带走三句话

1. **把"模型看得懂"换成"结构可引用"**——这是纯文本路线的全部秘密。
2. **能确定性验证的，永远不要交给模型**——模型只做选择和生成，不做校验。
3. **缺口不要绕过，要显性化并计量**——绕过产生技术债，计量才能收敛。
